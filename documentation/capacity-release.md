# MoneyQuest capacity release

Deploy the API and redacted login-diagnostics function before updating the clients. Keep both original deployment references for rollback. Use a dedicated staging Appwrite project, Railway environment, PostgreSQL database, Redis instance, and test notification routes. Confirm the Appwrite organization plan, service quotas, and allowed load with the account owner. The existing Development environment needs isolation verification before use.

1. Run Alembic through revision 20261114_10 and configure Railway to check /ready. Set RATE_LIMIT_REDIS_URL before running multiple replicas. Enable edge caching for /content/learning-path. Check that it returns public Cache-Control and ETag and that other authenticated endpoints stay private. Set a fixed total PostgreSQL connection budget, reserve capacity for migrations and other services, and divide the remaining connections across workers and replicas through DB_POOL_MAX_CONNECTIONS.
2. Record one-replica staging throughput before adding a second replica. Tune RL_GLOBAL_CAPACITY and RL_GLOBAL_REFILL_RATE separately from RL_IDENTITY_GLOBAL_CAPACITY, RL_IDENTITY_GLOBAL_REFILL, RL_IDENTITY_IP_CAPACITY and RL_IDENTITY_IP_REFILL. Measure per-school demand against the shared light IP limit. Keep protective defaults until staging measurements show a safe increase. Compare one and two replicas using the same aggregate DB pool, then repeat the successful target after removing one replica. Keep data for the 1,000-user rollout milestone and 3,000-user expansion.
3. Build the web preview and iOS/Android release previews against staging. Validate normal sign-in, public signup, a school account, recovery-link completion in mobile browsers, slow and offline connections, rate-limited responses, expired sessions, switching accounts in two browser tabs, and migration from the installed mobile versions. For the local browser check, run the web export, start node tests/serveDist.cjs and run node tests/authBrowserSmoke.cjs. Expand access after the real device checks pass.
4. Supply a JSON fixture array to tests/load/capacity.js. Each fixture contains id, email, password, and optionally name and profile. Provision returning accounts and their profile rows through the staging Users API and database only. For mixed testing leave every fifth fixture uncreated and supply a schema-valid profile payload. Use distinct fixture IDs and synthetic addresses. Keep the file outside Git. Split load among generators using separate fixture ranges, with a real school egress runner assigned pre-provisioned accounts only. Account creation rate caps apply per real egress IP.
5. Set STAGING_ISOLATION_VERIFIED=yes and APPWRITE_QUOTAS_VERIFIED=yes only after the checks above. Supply STAGING_APPWRITE_URL including /v1, STAGING_APPWRITE_PROJECT, STAGING_APPWRITE_DATABASE, STAGING_API_URL, FIXTURES, and USERS. Use WORKLOAD=returning, mixed, and sustained separately. For sustained tests also set LEVEL_ID and a unique RUN_ID. Run k6 run tests/load/capacity.js. Run each cohort at 1,000 before advancing to 3,000. Run the one-minute bursts alongside an already-warm cohort when verifying failure headroom. Fetch the staging receipt and progress rows after each synchronized wave and compare against the submitted attempts and rewards. The script verifies a repeated API receipt. Release clients must also prove Appwrite sync recovery.
6. Track valid sign-in and signup success, p95 sign-in, time to usable Home, unexpected 429s and timeouts, learning API latency, DB queue wait, and pool use. Require at least 99.5% valid sign-ins, sign-in and lesson-open p95 below 3 s, save p95 below 2 s, gameplay failure below 0.5%, and zero wrong-account sessions or lost/duplicate completions. Require a passing run on release devices and a healthy production pilot before widening each milestone. Pause on threshold regressions and roll back immediately on account-isolation or progress-integrity failure. Leave the additive receipt table in place during a client or API rollback.
